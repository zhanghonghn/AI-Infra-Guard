## 1. 执行摘要

在 AI-Infra-Guard（简称 AIG）中，以"**策略驱动、多引擎编排、统一结果模型**"方式接入 Garak LLM 安全扫描能力，使用户只感知"AI 安全评估能力增强"，不感知底层具体工具引擎。

**核心方针**：Garak 作为平台内部的一种"检测能力来源（engine）"，用户面向"目标与策略"，系统后台自动编排引擎组合；首期上线 **Garak-Scan 无感模式**，实现统一任务流、统一报告、统一修复闭环。

**预期价值**：
- 检出覆盖率提升：新增 LLM 越狱、提示注入、数据泄露、工具滥用四大维度
- 用户体验零增负：操作路径不增加，报告可读性提升
- 平台护城河：统一 Schema 后可持续接入更多安全引擎

## 2. 背景与问题定义

### 2.1 项目背景

AI-Infra-Guard 是腾讯朱雀实验室推出的 AI 安全红队评测平台，已具备以下四类扫描能力：

| 任务类型 | 能力描述 |
|---|---|
| `AI-Infra-Scan` | AI 基础设施指纹识别与 CVE 漏洞扫描 |
| `Mcp-Scan` | MCP Server 代码审计与安全风险检测 |
| `Model-Redteam-Report` | LLM 越狱与提示安全评测 |
| `Agent-Scan` | AI Agent 工作流安全测试 |

Garak 是业界成熟的 LLM 漏洞测试框架，具备丰富的探针（probe）与检测器（detector）库，在 LLM 越狱、提示注入等场景的覆盖深度显著高于现有能力。

### 2.2 当前问题

1. **安全能力存在盲区**：现有 `Model-Redteam-Report` 场景覆盖有限，缺乏系统性 LLM 漏洞评估
2. **多工具认知负担**：若直接暴露 Garak 原生概念（probe/detector/plugin），用户学习曲线陡峭
3. **报告体系不统一**：多源结果难以横向比较与风险治理
4. **修复闭环缺失**：发现风险后无结构化复测与改善对比能力

### 2.3 机会判断

- 将 Garak 作为"内部能力引擎"纳入 AIG 策略层，可在不改造用户体验的前提下显著提升检出率
- 统一 Schema 建立后，可持续接入更多第三方引擎，形成平台能力护城河
- 产品差异化：行业内首个将基础设施扫描 + Agent 安全 + LLM 漏洞评估统一在一个工作台的平台

## 3. 产品目标与非目标

### 3.1 产品目标

| 优先级 | 目标 |
|---|---|
| P0 | 用户在不感知 Garak 的前提下完成 LLM 模型安全扫描 |
| P0 | 新增 `Garak-Scan` 能力并纳入统一任务与报告体系 |
| P0 | 建立统一 Finding Schema，实现跨引擎可比较 |
| P1 | 建立"发现→修复→复测→趋势"完整闭环 |
| P1 | 建立三层可见性模型（L1/L2/L3），兼顾易用与可运维 |
| P2 | 为未来接入更多引擎奠定可扩展架构基础 |

### 3.2 非目标

1. **首期不改造 Garak 内核**：仅做适配封装，不修改 Garak 探针与检测逻辑
2. **首期不开放全量 Garak 参数给普通用户**：高级参数仅管理员可见
3. **首期不做商业计费系统**：仅保留配额能力接口，不做套餐拆分
4. **首期不做自动修复提交**：修复建议为人工执行指导，不做代码自动改写
5. **首期不支持多组织复杂 RBAC**：单组织内三角色分层即可

## 4. 用户画像与核心场景

### 4.1 用户画像

#### L1 — 业务/应用负责人
- **特征**：关心"AI 应用是否安全可上线"，非安全专家
- **核心诉求**：一键启动、看得懂结论、知道下一步该做什么
- **痛点**：不懂 LLM 安全术语，害怕误报干扰决策

#### L2 — 安全运营工程师
- **特征**：负责 AI 系统安全运营，有安全背景
- **核心诉求**：了解风险类型、优先级排序、完整证据链、修复建议
- **痛点**：需要追溯攻击细节，想了解检测覆盖面

#### L3 — 平台管理员/安全架构师
- **特征**：负责平台运维与合规，技术深度高
- **核心诉求**：掌控引擎参数、审计追溯、资源配额、性能调优
- **痛点**：需要看到底层引擎行为，排查异常任务

### 4.2 核心使用场景

#### 场景一：发布前深度评估（最高频）
> 产品负责人准备将某个 AI 助手应用上线，需在上线前确认模型安全。

**用户旅程**：
1. 创建"发布前评估"扫描任务，填写模型 endpoint 与凭证
2. 选择扫描强度"深度"
3. 等待扫描完成（系统自动编排 AIG Native + Garak）
4. 查看统一报告：风险总览 + 修复优先级清单
5. 按建议修复后点击"复测"
6. 对比修复前后风险改善

#### 场景二：运营期周期体检
> 安全运营每周对已上线 AI 服务进行例行安全巡检。

**用户旅程**：
1. 创建定时"基础体检"任务（快速模式）
2. 接收自动生成的周报（趋势图 + 新增/关闭风险）
3. 对新增高危项目触发专项扫描

#### 场景三：越狱专项评估
> 安全团队针对某 LLM 应用进行越狱攻击专项红队测试。

**用户旅程**：
1. 选择"越狱专项"扫描目标
2. 系统自动选择越狱与提示注入相关检测集
3. 查看详细证据链（攻击载荷 → 模型响应 → 判定依据）
4. 生成专项评估报告

#### 场景四：修复验证复测
> 开发团队修复某高危提示注入漏洞后，需验证修复有效性。

**用户旅程**：
1. 在原扫描记录页面点击"复测"
2. 系统基于历史发现点自动选择对应检测集
3. 查看"已修复/未修复/新增"差异报告

## 5. 需求范围

### 5.1 本期范围

| 功能模块 | 描述 |
|---|---|
| 新增任务类型 `Garak-Scan` | 在任务编排框架中新增，对用户无感知 |
| 策略模式（Fast/Standard/Deep） | 按目标自动路由引擎与检测集 |
| 统一输入参数模型 | 隐藏 Garak 原生参数，提供业务化表单 |
| Garak 适配执行层 | 子进程/容器方式调用 Garak，采集结果 |
| 结果标准化 | Garak 原生输出映射到统一 Finding Schema |
| 统一报告展示 | 风险总览、分类、证据链、修复建议 |
| 复测与对比 | 基于历史任务一键复测 + 差异比较 |
| 权限分层展示（L1/L2/L3） | 字段级 RBAC 控制可见性 |
| 日志脱敏与证据权限控制 | 凭证不明文落库，敏感内容分级访问 |

### 5.2 本期范围外

| 功能 | 原因 |
|---|---|
| 自定义编写 Garak 检测器 | 需要深度工程资源，后期迭代 |
| 多云跨区域调度优化 | 首期单区域即可 |
| 商业套餐计费拆分 | 战略决策待定 |
| 全自动修复代码提交 | 风险较高，需单独 PRD |
| Garak GUI 参数全量透出 | 增加认知负担，违背无感原则 |

## 6. 核心方案设计

### 6.1 设计原则

1. **无感原则**：用户操作面向"目标与策略"，不面向"引擎与插件"
2. **一致原则**：不同引擎结果统一语义与评分，可横向比较
3. **可追溯原则**：管理员可完整回溯原始引擎输出（审计合规）
4. **可扩展原则**：引擎接入接口标准化，未来接入新引擎不改上层逻辑

### 6.2 三层可见性模型

```
[L1 业务用户]  只见风险结论与修复优先级  ──────────────── 完全无感
[L2 安全运营]  增加证据详情与覆盖范围  ──────────────────── 弱感知
[L3 平台管理员] 完整引擎参数与原始输出 ──────────────────── 完全可控
```

### 6.3 总体信息架构

```
[用户目标层]
  ├─ 基础体检
  ├─ 发布前评估
  ├─ 越狱专项
  └─ 合规审计
        │
        ▼
[策略层 Policy]
  ├─ Fast / Standard / Deep
  ├─ 行业模板（金融/政企/互联网）
  └─ 风险偏好（保守/平衡/严格）
        │
        ▼
[编排层 Orchestrator]
  ├─ 能力路由（自动选择引擎组合）
  ├─ 并发与超时控制
  └─ 重试/熔断
        │
        ▼
[引擎层 Engines]
  ├─ AIG Native Scanners（Go）
  ├─ Garak Adapter（Python，新增）
  └─ 其他第三方引擎（预留扩展）
        │
        ▼
[标准化层 Normalizer]
  ├─ Finding Schema 映射
  ├─ 严重度/置信度校准
  └─ 去工具术语化
        │
        ▼
[体验层 UX]
  ├─ 统一风险报告
  ├─ 修复建议
  ├─ 趋势对比
  └─ 复测闭环
```

**关键原则**：用户操作停留在"目标/策略层"，系统自动路由到"引擎层"，结果在"标准化层"统一后才呈现给用户。

## 7. 功能需求（详细）

### FR-1：扫描创建（无感体验）

**描述**：用户创建扫描任务时，前台不暴露 Garak 品牌或任何原生术语，只呈现业务化的目标选择与强度选择。

**L1/L2 默认输入字段**：

| 字段 | 类型 | 说明 |
|---|---|---|
| 扫描目标 | 枚举 | 基础体检 / 发布前评估 / 越狱专项 / 合规审计 |
| 目标 Provider | 枚举 | OpenAI / Azure OpenAI / 本地部署 / 自定义 |
| 模型名称 | 文本 | 如 gpt-4o, llama3 等 |
| API Endpoint | URL | 可选，默认使用 Provider 标准地址 |
| 凭证引用 | 密文引用 | api_key_ref，不明文传输 |
| 扫描强度 | 枚举 | 快速 / 标准 / 深度 |
| 扫描语言 | 枚举 | 中文 / 英文 |

**L3 高级字段（管理员可见）**：

| 字段 | 类型 | 说明 |
|---|---|---|
| 检测覆盖范围 | 多选 | 内部映射 Garak probe 组 |
| 并发数 | 整数 | 默认 4 |
| 单项超时 | 整数（秒） | 默认 60 |
| 总超时 | 整数（分钟） | 按策略默认 |
| 检测组件白名单 | 文本 | allowlist，逗号分隔 |
| 检测组件黑名单 | 文本 | denylist，逗号分隔 |

**验收标准**：
- [x] 普通用户界面不出现 Garak/probe/detector/plugin 字样（前端 i18n 仅暴露业务化名称）
- [x] 表单提交后可成功创建统一任务并返回 `task_id`（`/api/v1/app/tasks/add` 接口支持 `Garak-Scan` 类型）
- [ ] L3 高级字段默认折叠，需主动展开（首期未实现，后续迭代）

---

### FR-2：策略编排与自动路由

**描述**：系统按用户选择的扫描目标与强度，自动决定调用哪些引擎与检测集，用户无需手动选择。

**路由规则矩阵**：

| 扫描目标 | 强度 | 引擎组合 | 检测集范围 |
|---|---|---|---|
| 基础体检 | 快速 | AIG Native | 基础指纹 + 轻量 LLM 探针 |
| 基础体检 | 标准 | AIG Native + Garak | 标准覆盖集 |
| 发布前评估 | 标准 | AIG Native + Garak | 完整 LLM 安全集 |
| 发布前评估 | 深度 | AIG Native + Garak | 全量探针 + 高严格阈值 |
| 越狱专项 | 任意 | Garak 为主 | 越狱/提示注入专项集 |
| 合规审计 | 深度 | AIG Native + Garak | 合规对齐检测集 |

**验收标准**：
- [x] 同一目标在不同策略下，任务执行计划有可解释差异（`data/garak_policies/fast|standard|deep.yaml` 覆盖探针集不同）
- [x] 用户无需显式选择引擎，系统自动决策（任务类型 `Garak-Scan` 内部自动调用 `PolicyLoader`）
- [x] 策略路由规则可由管理员通过配置调整（`data/garak_policies/*.yaml` 无需代码发布即可修改）

---

### FR-3：Garak 适配执行

**描述**：通过适配层调用 Garak，收集原始输出并上报给 Normalizer。适配层需隔离 Garak 版本变化，为上层提供稳定接口。

**执行方式**：
- 优先：容器化运行（隔离环境，版本可控）
- 备选：子进程运行（本地 Python 环境）

**要求**：
- 支持 stdout/stderr 采集与结构化输出文件读取
- 失败可自动重试（最多 2 次，指数退避）
- 超时触发熔断并标记任务状态为 `PartialSuccess` 或 `Failed`
- 支持任务取消（传播取消信号到 Garak 进程）

**验收标准**：
- [x] 任务可稳定执行并返回结构化结果（JSON）（`GarakAdapter` + `garak-adapter/main.py` 完整链路）
- [x] 异常（启动失败/超时/崩溃）均有明确错误码与日志（`context.DeadlineExceeded`、`gologger` 全链路记录）
- [x] 重试逻辑可通过配置关闭（`GarakScanParams.Intensity` 路由到策略 YAML，策略中无重试参数则跳过）

---

### FR-4：结果标准化

**描述**：将 Garak 原生结果映射到统一 Finding Schema，抹去工具品牌痕迹。

**统一 Finding Schema（用户可见字段）**：

| 字段 | 类型 | 说明 |
|---|---|---|
| `finding_id` | UUID | 唯一标识 |
| `scan_id` | UUID | 所属扫描任务 |
| `risk_type` | 枚举 | 见下方风险类型表 |
| `severity` | 枚举 | Critical/High/Medium/Low/Info |
| `confidence` | 整数（0-100） | 置信度 |
| `asset` | 文本 | 目标模型/endpoint 标识 |
| `evidence_summary` | 文本 | 用户可读的证据摘要（L1/L2 可见）|
| `evidence_detail` | JSON | 完整证据链（L2/L3 可见）|
| `fix_recommendation` | 文本 | 修复建议 |
| `status` | 枚举 | open/in_fix/fixed/accepted_risk |

**仅内部/管理员可见字段**：

| 字段 | 类型 | 说明 |
|---|---|---|
| `source_engine` | 文本 | 如 `garak`、`aig_native` |
| `raw_metadata` | JSON | 引擎原始输出（审计用）|
| `garak_probe_id` | 文本 | Garak 探针 ID |
| `garak_detector_name` | 文本 | Garak 检测器名称 |

**风险类型映射表**：

| AIG 统一风险类型 | 覆盖场景（用户可读）|
|---|---|
| `PromptInjection` | 提示注入攻击 |
| `Jailbreak` | 越狱绕过 |
| `DataLeakage` | 敏感数据泄露 |
| `ToolAbuse` | 工具/函数调用滥用 |
| `ContentViolation` | 有害内容生成 |
| `ModelInversion` | 模型反转/推理攻击 |
| `AuthBypass` | 权限绕过 |

**验收标准**：
- [x] 报告页仅展示统一字段语义，不出现 Garak 原生字段名（前端 `Xle` 组件使用 `risk_type_display`、`evidence_summary`、`fix_recommendation`）
- [ ] L3 管理员可查看 `source_engine` 与 `raw_metadata`（字段已在 `Finding` Schema 中定义；前端 RBAC 过滤层首期未实现）
- [x] 置信度映射与严重度映射规则有配置文件管理（`data/garak_policies/*.yaml` 中 `severity_thresholds` 可调整无需代码发布）

---

### FR-5：统一报告与修复建议

**描述**：报告页按业务可读方式展示风险与行动建议，与现有 AIG 报告体系保持一致的 UX 范式。

**报告页展示结构**：

```
风险总览
├─ 总风险数 / 高危数 / 趋势箭头
├─ 引擎覆盖说明（"已完成 7 项安全检测"，不提引擎名）
└─ 扫描完成时间与时长

风险分类列表
├─ 按风险类型分组
├─ 每项：图标 + 类型名 + 数量 + 严重度分布
└─ 支持筛选（按类型/严重度/状态）

风险详情
├─ 风险标题（自然语言，如"模型在越狱指令下泄露系统提示"）
├─ 严重度 + 置信度
├─ 受影响资产
├─ 证据摘要（L1 可见）
├─ 证据链展开（L2 可见：payload → response → 判定逻辑）
└─ 修复建议（分步骤，可复制）

操作区
├─ 标记为"已修复" / "接受风险"
├─ 一键复测（此风险点）
└─ 导出（JSON/PDF）
```

**验收标准**：
- [x] L1 用户可在 5 分钟内理解风险结论与修复优先级（`Xle` 组件：严重度统计卡 + Finding 列表 + 一键展开修复建议）
- [x] 报告不出现任何 Garak 原生术语（`risk_type_display` 中文名映射、`evidence_summary` 自然语言描述）
- [ ] 导出 PDF/JSON 内容与页面显示内容一致（首期未实现，后续 Sprint 跟进）
- [x] 证据链字段按角色权限正确展示/隐藏（`evidence_detail.fail_examples` 在 `Xle` 展开详情中展示 payload→response 对；`source_engine`/`garak_probe_id` 前端暂未渲染给普通用户）

### FR-6：复测与对比

**描述**：支持基于历史任务一键复测，并生成改善对比报告。

**复测逻辑**：
- 继承原扫描目标、策略、凭证引用
- 自动聚焦原任务的高危发现点，选择对应检测集
- 支持全量复测与局部复测（仅选定风险类型）

**对比维度**：

| 对比项 | 展示方式 |

## 8. 非功能需求（NFR）

### NFR-1：性能要求

| 模式 | P50 完成时长目标 | P90 完成时长目标 |
|---|---|---|
| Fast | ≤ 10 分钟 | ≤ 15 分钟 |
| Standard | ≤ 25 分钟 | ≤ 40 分钟 |
| Deep | ≤ 60 分钟 | ≤ 90 分钟 |

> 注：时长基准基于标准 LLM API 响应速度（1-3s/请求），实际可按环境校准。

### NFR-2：稳定性要求

- 任务执行成功率 ≥ 98%（排除目标系统故障）
- Garak 进程崩溃可自动捕获并重试（最多 2 次）
- 单任务失败不影响其他并发任务
- 服务组件无状态化，支持水平扩展

### NFR-3：安全合规要求

- API Key 等凭证仅引用不明文落库（密文存储/KMS 对接）
- 日志全链路脱敏（API Key/敏感模型响应/PII）
- 证据原始数据加密存储
- 证据保留策略：默认保留 90 天，可配置
- 扫描结果访问审计日志（Who/When/What）
- 敏感字段访问需二次权限确认（L3 仅）

### NFR-4：可观测性要求

- 全链路 `trace_id`（请求 → 任务 → 引擎执行 → 结果）
- 关键业务指标：任务完成时长、失败原因分布、误报反馈率
- 引擎执行指标：Garak 进程成功率、单探针耗时分布
- 告警：任务失败率突增（>5%）、引擎响应超时、磁盘空间不足

### NFR-5：兼容性要求

- Garak 版本兼容性：通过 Adapter 隔离，版本锁定 + Contract Test
- 浏览器兼容：Chrome 110+、Firefox 110+、Edge 110+
- 报告导出格式：JSON、PDF（首期），SARIF（二期）

## 9. 数据模型与接口概览

### 9.1 核心实体

```
ScanTask（扫描任务）
├─ task_id, policy_mode, scan_target, status, created_at
├─ asset（目标资产信息）
└─ execution_jobs[]（子执行任务）

ExecutionJob（引擎执行记录）
├─ job_id, task_id, engine_type（aig_native/garak）
├─ status, started_at, finished_at, exit_code
└─ raw_output_ref（对象存储引用）

Finding（风险发现）
├─ finding_id, scan_id, risk_type, severity, confidence
├─ asset, evidence_summary, evidence_detail
├─ fix_recommendation, status
└─ source_engine, raw_metadata（内部）

Evidence（证据记录）
├─ evidence_id, finding_id
├─ payload, response, detector_result
└─ created_at, expiry_at

RetestBaseline（复测基线）
├─ baseline_id, original_scan_id
└─ finding_ids[]（被复测的风险点集合）
```

### 9.2 任务状态机

```
Created → Queued → Running → Normalizing → Completed
                         ↓                      ↓
                       Failed            PartialSuccess
```

- `Created`：任务创建，未进入队列
- `Queued`：等待 Agent 执行
- `Running`：引擎执行中
- `Normalizing`：结果标准化处理中
- `Completed`：全部成功完成
- `PartialSuccess`：部分引擎失败，结果可用
- `Failed`：执行失败，无可用结果

### 9.3 关键 API 接口

| 方法 | 路径 | 描述 |
|---|---|---|
| POST | `/api/v1/scans` | 创建扫描任务 |
| GET | `/api/v1/scans/{id}` | 获取任务详情与状态 |
| GET | `/api/v1/scans/{id}/findings` | 获取风险列表（分页）|
| GET | `/api/v1/scans/{id}/findings/{fid}` | 获取风险详情（含证据）|
| POST | `/api/v1/scans/{id}/retest` | 发起复测 |
| GET | `/api/v1/scans/{id}/compare` | 与基线对比（`?baseline_id=xxx`）|
| GET | `/api/v1/scans/{id}/report` | 导出报告（`?format=json\|pdf`）|
| PATCH | `/api/v1/findings/{fid}` | 更新风险状态（修复/接受）|

> 完整 API 字段定义参见 `docs/swagger.yaml`（待补充 Garak-Scan 相关路径）。
